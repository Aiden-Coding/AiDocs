Java 服务端通用设计实践

本文整理框架无关的服务端设计约定，适用于 Spring MVC、WebFlux 或其他 Java Web 技术。它关注 API 契约和失败行为；具体控制器、校验器与异常处理实现见现有 Spring MVC 专题。

1. 设计清晰的 API 契约​

每个接口应定义用途、请求字段、响应字段、认证要求、错误情况和兼容性约束。资源路径使用名词表达资源，HTTP 方法表达操作语义；状态码应准确区分成功、客户端错误、未认证、无权限、资源不存在和服务端故障。

分页接口应明确页码从零还是一开始、默认与最大页大小、排序字段白名单和稳定排序规则。列表响应应包含必要的分页信息，避免隐含的全量读取。

请求和响应 DTO 与数据库实体分开。这样可避免数据库结构变更直接破坏 API，也能控制对外暴露字段。新增可选字段通常比改变现有字段含义更兼容；破坏性变更应通过版本或迁移策略管理。

2. 输入校验与错误响应​

在请求边界校验必填项、格式、长度、范围和跨字段约束。校验失败时返回稳定的错误结构，包含机器可识别的错误码、可读消息和字段级问题；不要把堆栈、SQL、内部类名或敏感数据返回给客户端。

错误响应应区分客户端可修正的问题和服务端故障。日志中保留异常根因与请求关联标识，客户端只接收适合公开的描述。校验和权限检查之外，业务层仍需保护不变量，不能仅依赖前端校验。

3. 幂等性与重试​

网络超时并不能说明服务端没有完成操作。对创建订单、扣款等会产生副作用的操作，应设计幂等键或业务唯一约束，使重复请求不会重复产生结果。幂等记录需要明确作用域、有效期、并发冲突处理和返回语义。

重试只用于可恢复的错误，并设置次数上限、退避和总超时预算。非幂等操作不得因超时而直接重复执行；跨服务调用需要把幂等策略与下游能力一起设计。

4. 配置、日志与敏感信息​

配置按环境注入，区分默认值、必填项和秘密信息。启动时尽早校验关键配置，避免请求到达后才因缺失配置失败。秘密应由受控密钥系统提供，不写入源码、镜像或普通日志。

日志记录事件时间、级别、服务与环境、请求关联 ID、操作结果和必要的业务定位字段。避免记录密码、访问令牌、完整支付信息或不必要的个人信息。对高频路径控制日志量，并使用指标记录请求量、延迟和错误率，避免只靠日志发现故障。

5. 缓存与消息队列的使用边界​

缓存需要定义键、过期时间、更新和失效策略，并考虑空值缓存、热点键、并发重建和数据一致性。缓存不能替代数据正确性约束；删除或更新数据时，应明确缓存如何同步失效。

消息队列适合解耦、削峰和异步处理，但引入后要处理重复投递、消费失败、重试、死信和顺序要求。消费者应具备幂等性，并通过监控关注积压、失败率和消费延迟。不要将“消息已发送”误认为“业务最终完成”。

6. 安全与可观测性衔接​

所有输入都视为不可信数据，使用参数化数据库访问、输出编码和最小权限策略。认证回答“是谁”，授权回答“能做什么”；不要只依赖网关鉴权，服务自身也应保护敏感操作。

为请求建立可跨线程、跨服务传递的关联标识，并统一记录日志、指标和链路追踪。结合现有的 Spring Security 和可观测性专题，形成从请求入口到下游依赖的诊断链路。

设计检查表​

  • API 契约说明输入、输出、状态码、错误结构和兼容策略。
  • 参数边界在服务端校验，错误响应不泄露内部细节。
  • 有副作用的操作具备幂等或唯一性保护，重试有边界。
  • 配置与密钥按环境管理，日志不会泄漏敏感数据。
  • 缓存和消息队列的重复、失败、积压场景有处理策略。
  • 请求能通过关联标识在日志、指标和追踪中定位。
