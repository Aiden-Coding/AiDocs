# Java 服务部署与运行基础

本文介绍 Java 服务从构建制品到容器运行和基础排障的通用流程。生产部署方式因组织平台而异；命令和检查项应结合目标操作系统、容器运行时及编排平台调整。

## 1. 部署制品与环境配置

部署应使用可追踪、不可变的制品，例如带版本号或提交标识的可执行 JAR 或容器镜像。开发、测试和生产环境应晋级同一制品，避免每个环境重新构建导致内容漂移。

将环境差异通过环境变量、配置文件或配置服务注入。区分非敏感配置与密钥；密钥通过受控密钥管理方式提供，不写入代码仓库、镜像层或命令历史。启动时校验必需配置，并提供不含秘密值的有效配置摘要，便于确认实际运行环境。

## 2. Linux 上的启动与停止

前台启动便于本地观察；服务管理器或容器平台应负责生产进程生命周期和自动重启。不要用 shell 后台化代替可靠的进程管理。

```bash
java -Xms512m -Xmx512m -jar app.jar --spring.profiles.active=prod
```

停止服务时先发送正常终止信号，让应用完成请求、提交必要状态并关闭连接池；设置合理的优雅停机超时，再由平台强制结束卡住的进程。应用和平台的停机期限要互相匹配。

常用排查命令包括 `ps` 查看进程、`ss -lntp` 查看监听端口、`df -h` 查看磁盘空间、`free -h` 查看内存概况，以及 `journalctl` 或容器日志命令查看服务日志。命令输出可能包含敏感信息，分享前应脱敏。

## 3. Docker 镜像与容器

镜像构建应使用可重复的构建步骤，尽量采用多阶段构建，将运行时镜像与编译工具链分开。基础镜像应固定受支持的版本并定期更新。容器以非 root 用户运行，只暴露必需端口，并通过只读文件系统或明确的数据卷控制可写路径。

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
COPY target/app.jar /app/app.jar
USER 10001
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

容器内存上限可能小于宿主机内存。为 JVM 堆、元空间、线程栈、直接内存和本地库预留空间；根据容器限制配置 JVM，并通过运行指标验证实际占用。不要假定 `-Xmx` 等于容器可用的全部内存。

## 4. 健康检查与可观测性

存活检查用于判断进程是否仍能工作；就绪检查用于判断实例是否适合接收流量。检查应轻量、快速，避免每次探测都触发昂贵的深度依赖调用。下游暂时不可用时如何影响就绪状态，应结合服务是否还能提供部分功能来决定。

服务至少应提供可查询的版本/构建标识、请求成功率与延迟、错误率、线程池和连接池状态，以及 JVM 堆和 GC 指标。日志输出到标准输出或统一采集位置，采用可检索的结构化字段，并携带请求关联标识。

## 5. 基础故障排查流程

1. 确认影响范围、开始时间、最近发布和配置变更。
2. 查看进程是否存在、端口是否监听、健康检查状态和容器重启记录。
3. 对照请求延迟、错误率、资源使用、GC、线程池与数据库连接池指标定位瓶颈。
4. 查看相关时间段日志和链路追踪，确认故障位于应用还是下游依赖。
5. 先恢复服务，再保留必要诊断信息；变更配置或回滚后继续观察指标。

排障时先收集证据再终止进程或清理容器。线程转储、堆转储和完整日志可能包含个人数据或凭据，应限制访问并遵循组织保留策略。

## 6. 发布与回滚

发布前确认制品版本、配置、资源限制、健康检查和数据库变更兼容性。优先采用可逐步切流的发布方式，并设置成功率、延迟和错误率等回滚条件。数据库变更应尽量采用兼容性迁移：先增加兼容结构，再迁移读写逻辑，最后清理旧结构。

回滚不仅是恢复旧镜像，也要确认配置和数据库变更仍与旧版本兼容。发布后观察关键指标，达到预设稳定窗口后再完成发布。

## 运行检查表

- 制品有唯一版本标识，环境之间晋级同一个构建结果。
- 配置与密钥从外部注入，启动校验不会泄露秘密。
- 容器使用非 root 用户，资源限制为 JVM 留出本地内存空间。
- 优雅停机、健康检查、日志采集和关键指标均已配置。
- 发布和数据库迁移有观测指标、回滚条件与兼容方案。
