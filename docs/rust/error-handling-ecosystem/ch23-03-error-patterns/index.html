错误处理模式与最佳实践

选择 thiserror 或 anyhow 只是起点。健壮的错误处理还需要决定错误在哪一层转换、何时增加上下文、哪些错误可重试，以及何时向用户展示。

在边界处选择错误类型​

库 API 应提供有意义且稳定的错误类型，让调用方能按变体处理；应用通常可以在边界处将不同来源的错误聚合为动态错误并附加操作上下文。

use anyhow::Context;
use std::path::Path;

fn load_config(path: &Path) -> anyhow::Result<Config> {
    let text = std::fs::read_to_string(path)
        .with_context(|| format!("读取配置文件 {}", path.display()))?;
    let config = toml::from_str(&text)
        .with_context(|| format!("解析配置文件 {}", path.display()))?;
    Ok(config)
}

不要过早把错误转换成字符串。保留源错误和类型，诊断工具才能展示错误链，调用方也能检查具体原因。库若需要映射底层错误，使用领域错误类型并保留 source。

在合适的层级增加上下文​

底层错误通常说明“发生了什么”，上层上下文补充“正在做什么”。在调用边界增加少量、稳定且有用的信息：

  • 文件 I/O：路径、读写动作。
  • 网络或数据库：目标服务、操作名称和可关联的请求标识；不要记录秘密或敏感载荷。
  • 解析：格式、来源位置或字段名。

避免在每一层重复包装相同信息，也不要用上下文覆盖根因。面向用户的消息与内部诊断可分开处理。

区分可恢复错误与程序缺陷​

  • 输入无效：返回验证错误，让调用方修正输入。
  • 环境或 I/O 故障：返回错误，并由应用决定提示、降级或重试。
  • 暂时性故障：只有在操作具备幂等性或有去重机制时才重试；使用有界次数、退避和抖动。
  • 违反内部不变量：测试和调试阶段可使用断言；不要用 unwrap 把外部输入或常规 I/O 失败变成意外 panic。

panic! 适用于无法合理恢复的程序错误，不应取代普通业务错误。反过来，也不要把所有问题都压成一个无法区分的字符串错误。

让错误传播清晰​

? 适合沿调用栈传播错误；在需要提供操作上下文、做恢复决策或释放特定资源时显式匹配：

match fetch_record(id).await {
    Ok(record) => use_record(record),
    Err(error) if is_transient(&error) => retry_with_backoff(id).await?,
    Err(error) => return Err(error).context("获取记录失败"),
}

重试分支应基于明确的错误分类，避免对永久错误无限重试。超时也不保证远端未执行操作；必要时通过事务、幂等键或查询操作结果解决不确定状态。

可观测性与安全​

记录错误时保留错误链和关联上下文，但避免把密码、令牌、个人数据或完整请求正文写入日志。对高频错误进行采样或聚合，防止故障时日志洪泛。用户可见消息应稳定且可操作，详细技术原因放入受控诊断信息。

测试错误路径​

除成功路径外，还应验证：

  • 错误类型、分类与源错误是否保留。
  • 上下文是否足以定位失败操作。
  • 重试次数、超时和取消边界是否符合预期。
  • 外部输入或依赖故障是否返回错误而非意外 panic。

库可用单元测试验证错误变体；应用可通过集成测试确认日志、退出状态和用户提示。
